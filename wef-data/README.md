# Recurring wef-data

## Approved bounded source recovery — 29 October 2026

Only explicit HTTP502/503/504 and explicit read timeouts may defer the same scheduled checkpoint. There are at most three scheduled retries per request in a run, using the existing recovery lane delays (initial60seconds, exponential, bounded by its maximum). A fourth failed attempt stops normally. HTTP403/otherstatuses, decoding failures, identity/scope violations and malformed responses remain hard failures. No immediate reader retry, task cadence change, key change or manual collector is introduced.

Validated class and dated-schedule responses are saved individually with scope and content hashes. A resumed parallel batch fetches only missing responses, in the same reserved order, and stages no class facts until the full batch validates. Inventory caches are tied to the existing observation start ordinal: interrupted passes reuse captured responses, while a new pass in the same run must read fresh source. Directory capture already preserves its successful pages and keeps that implementation.

Private `runtime/source-deferred.json` stores source backoff separately from Airtable uncertain-write and retirement state. Every source error has its own retained private receipt in `runtime/source-errors/`, in addition to ordinary attempt/error logging. A successful completed revision clears source backoff; error receipts remain. A previously declared hard stop still requires an exact owner-approved resume receipt. Exhaustion and all other hard failures never auto-resume.

## Saved-write recovery and bounded initial directory — 29 October 2026

Scheduled code reserves Data rows using Airtable PATCH performUpsert matched solely on each existing primary-key field, at most ten records per request. It sends only the unchanged key, verifies returned IDs by readback, then uses the existing field/link staging and verification. A lost response resumes from saved input and matches the same keys; no blind POST replay or new identity builder. Legacy unknown-POST reservations must match the exact saved active/pending current-show owner before using this same reservation path. Current-show changes leave old checkpoint retirement to the existing rollover path.

Directory acquisition admits at most twelve requests per scheduled attempt, at most four in flight. Saved validated pages and the final first-page consistency check remain. Later attempts persist only newly captured pages; they still preflight the full capture for identity conflicts. Large directories therefore continue across ordinary invocations without bulk-restaging every prior page. Class batches stay at four; the existing 180-second admission budget and lane intervals are unchanged. An in-flight persistence/readback unit may finish after that budget: it is not a hard total-duration guarantee. Airtable work happens during row reservation, field/link upsert, evidence retention and readback; it does not consume model tokens. No agent is on the execution path.

Acceptance requires actual saved-key recovery, successful normal Data revisions and repeats, preserved original IDs/keys, observed source/persistence timings and actual due/backlog evidence. Offline new-show fixtures do not establish a naturally observed new-show first-load time. No task starts, state repairs, schema changes or key changes are part of verification.
